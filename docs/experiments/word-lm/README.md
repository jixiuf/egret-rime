# 实验：给搜索器换词级 LM（已否证，2026-10-16）

## 想解决什么

`nnxcyiwug`（已经+就位 的简码序列）被搜索器算成「已经义务一」并注入首位；
`tgynlwtyif`（重启输入法）被算成「第一遍输入法」。根因被认为是
**两条解码链各持一把尺子**：引擎 `script_translator` 用万象**词级** gram，
搜索器 `py_composer` 用**字级** `lm_rerank`。设想：给搜索器也换成词级 LM，
两条链用同一把尺子，注入就安全了。

## 做了什么

`gen_word_lm.py`：采样 150MB 语料（`data/corpus/clean/short/*.txt`）→ jieba 分词 →
统计 1/2/3-gram → 输出条件对数概率增益（bigram = log((c+1)/(c_prev+1))×1000 等），
取 top-K（300k+300k），写成「48-bit 哈希 + i16 值」的定长记录二进制包（Lua 侧二分查表）。

离线打分（自然词切分）**四个 case 全判对**：
```
  -27.33  已经|就位      >  -35.85  已经|义务|一
  -29.43  重启|输入法     >  -30.06  第一遍|输入法
  -47.47  渐渐|地|就|好|了 >  -48.65  渐渐|地|一号|了
  -51.09  希望|你|能|赶得上 > -63.96  希望|你|能|干的商
```

## 为什么否证

把打分换成**搜索器实际的切分**后，结论翻转：
```
  -38.15  已经|就|位      <  -35.85  已经|义务|一     ← 判错（"就位"被切成"就|位"）
```
两处根因：

1. **切分口径不一致**。搜索器是按**输入码**切的（`nnxc|yi|wug` → `已经|就|位`），
   而语料/jieba 是自然词切分（`就位` 是一个词）。于是 `就|位`、`重|启`、`第|一`、
   `输|入` 这些 bigram 在语料里 **count=0**，词级表对不上。
2. **引擎真正的 LM 是编译产物**（`wanxiang-lts-zh-hans.gram`，octagram 二进制，
   由词切分文本训练、但查询是**字符** n-gram）。Lua 侧无法复刻；项目自训的
   `zh-hans-egret.2_6gram.tsv` 是**原始字符** n-gram（不区分词边界），不等价。

⇒ 「在 Lua 里造一把和引擎同源的词级尺子」这条路不成立。

## 附带发现（对设计有用的）

- 搜索器注入对 640 条混打整句集的**净影响为 0**（开/关都 164/640，逐模式相同）；
  它救 `ililfbyihaole`，却毁 `nnxcyiwug`/`tgynlwtyif`。
- `ililfbyihaole` 引擎侧切分其实是对的（`il il fb yi hao le`），错在**选词**：
  `yi` 被读成拼音「一」而非五笔「就」、`hao` 读成「号」而非「好」。
  词权重其实站正确解（就 804 + 好 983 > 一 848 + 号 791；好了 803 > 一号 673），
  是万象 grammar 把它翻了过去。
- `nnxcyiwug` 搜索器错解「已经义务一」用的是**拼音词「义务」**（权重 14279）+
  「一」（16620），压过五笔读法「就」（804）+「位」——搜索器的词一元被拼音词带偏。
