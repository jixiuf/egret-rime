# 调研：如何提高五笔拼音混合输入体验

> 2026-09-29 ｜ 基于本仓库实测（rime_api_console + 黄金用例 + 整句评测）
> 相关：`docs/PROGRESS.md` §4.11（LM 重排）§4.15（统一搜索器/交付受阻）§4.16（整句词库）

## 0. 一句话结论

混流体验的瓶颈**不在搜索算法，而在候选裁决权**：
五笔「短码序列」能不能组句，取决于**传统库是否开启组句**（`enable_sentence`）；
组出来的句子能不能排第一，取决于**传统库与混合库的 `initial_quality` 落差（1000 : 1）**。
两个都是**纯配置**，且"重排既有候选"已被证明是**安全**的交付手段。

## 1. 实测痛点清单

| # | 输入 | 首候选 | 期望 | 现象 | 根因 |
|---|---|---|---|---|---|
| P1 | `qktqn` | 名称嗯 | 我吃饭 | 五笔短码序列**完全不组句** | 传统库 `enable_sentence: false` + 精确词组「名称」(`qktq`) 短路 |
| P2 | `qktnqnr` | 名秘饭 | 我吃饭 | 一/二级简码**前缀歧义**：一级 `q`=我 vs 二级 `qk`=名 | librime 分段取 `qk\|…\|…`，且该分段权重更高 |
| P3 | `trwuktnqnr` | 我们吃饭 ✓ | — | **无歧义时是对的** | 印证 P2 是歧义而非编码问题 |
| P4 | 五笔整句 | 传统库精确定位候选**恒压**混合库整句 | 整句该赢 | 混合库的 LM 组句永远看不到 | `initial_quality`：传统库 **1000** vs 混合库 **1** |
| P5 | 拼音长句 | 26% 完全命中 | 更高 | **66% 正确句进不了候选**（`max_sentences` 20→300 仅 34%→36%，耗时 0.3s→6.1s） | 候选生成是主瓶颈，不在排序 |
| P6 | 五笔候选 | 无拼音提示 | 显示拼音 | 拼音反查已配（`` `[a-z]*'?$ `` / `u[a-z]*'?$`），但 **`wubi_comment` 被注释掉** | `egret_wubi_py.schema.yaml:180-181` |
| P7 | 4 码输入 | 顶功上屏 | — | `auto_select: true` + `^[a-df-zA-DF-Z]\w{3}`（满 4 码自动上屏） | 五笔肌肉记忆；**实测对 P1/P2 无影响**（不是成因） |

**已确认好用的场景**：`trwuktnqnr→我们吃饭`、`taiwan/ckiy→台湾`、`tffu→等`、`tgtj→生不逢时`（用户词组）、
`jintiandetianqizenmeyang→今天的天气怎么样`（混合库 LM 组句）。

## 2. ⭐ 突破口：`enable_sentence` + 「共识重排」

> ### ⚠️ 重要修正（用户指出）
> **传统库开组句只适合纯五笔，不适合混合输入**：传统库只有五笔码，
> 对 `qchifanle`（q 五笔 + chifan 拼音）**根本无法解析** ✗。
> 混合输入必须由**混合库**（同时含五笔码与拼音音节）组句。
> 因此 §2.1 只适用于「纯五笔短码序列」这一子场景，不能作为混流方案。

### 2.0 混流真正的缺口：混合库的分段裁决偏向五笔读法

实测（同一输入，混合库 vs 我们的统一搜索器）：

| 输入 | 混合库现状 | 统一搜索器 | 说明 |
|---|---|---|---|
| `q` | 我 ✓ | 我 ✓ | 一级简码正常 |
| `chifan` | 吃饭 ✓ | 吃饭 ✓ | 纯拼音正常 |
| **`qchifanle`** | **色步犯了 ✗** | **我吃饭了 ✓** | **混在一串里 → 混合库选错读法** |
| `qktqn` | 名称嗯 ✗ | 我吃饭 ✓ | 纯五笔短码亦选错 |
| `wmchifan` | 人同吃饭 ✗ | 人同吃饭 ✗ | **简拼（声母缩写）两边都不支持** |

**根因**：混合库的拼音字表权重被刻意压低过（×0.35，为避免压掉五笔简码）→
**拼音读法系统性处于劣势**，于是混流字符串被拆成「五笔读法」的垃圾组合。
→ 这也是 §4.17「拼音字表 ×0.35 → 黄金 17/20」那次实验的真正含义：
   该系数是**简码保护**与**混流组句**之间的取舍旋钮。

### 2.1 传统库开组句 → 五笔短码序列立刻能组句（仅纯五笔，见上方修正）

`egret_wubi.enable_sentence: true` 后（配合已有的 `enable_completion: true`）：

```
qktqn    → 我吃饭      ← q(我) + kt→吃(ktn 补全) + qn→饭(qnr 补全)
qktnqnrb → 我吃饭了     trwuktnqnr → 我们吃饭
```

**原理**：`enable_completion` 让 `kt` 能补全成 `吃`(ktn)、`qn` 补全成 `饭`(qnr)，
于是**用户敲的短码序列就能被组句**——这正是五笔用户期望的行为。

**代价**：拼音也会走传统库的组句，产生**垃圾句**（`wojintianmeiyoukong → 伙晃发泄届膛亦咪怀`），
且因 `initial_quality: 1000` 置顶把正确的拼音整句压到第 4 位 → 黄金 15/20。

### 2.2 交付机制：只**重排**既有候选（安全）

`lua/compose_filter.lua` 改造为「共识重排」：
用统一码表搜索器（`py_composer`，支持五笔/拼音/混流）算出整句后，
在既有候选里找**同一个句子**并移到最前。

> **为什么安全**：`long_word_filter` 长期在 filter 里重排候选且无问题；
> 而**新增候选**（无论区间怎么取）或**改写候选文本**（`cand.text=` 对 Sentence/Phrase 静默无效）
> 都会让引擎中途提交 → 见 PROGRESS §4.15 的四条封死路径。

### 2.3 两者合起来的效果

| 配置 | 黄金 | 五笔整句 |
|---|---|---|
| 基线（传统库不组句） | **20/20** | ✗ `qktqn→名称嗯` |
| + 传统库组句 | 15/20 | ✓（但拼音垃圾句置顶） |
| + 传统库组句 + 共识重排 | **18/20** | ✓ `qktqn→我吃饭`、`qktnqnrb→我吃饭了`、`trwuchifan→我们吃饭` |

剩余 2 条失败：
- `tgtj → 重复`（4 码，我们的整句压掉了用户词组「生不逢时」）→ **加长度门槛（仅 ≥5 码重排）可解**
- `wojintianmeiyoukong → 伙晃发泄届膛亦咪怀`（搜索器算成「我今天没有中断一」，
  正确句在候选第 4 位 → 没匹配上，垃圾句仍置顶）→ 需「**非匹配的 Sentence 候选降至匹配者之后**」

**当前默认关闭**（`enable_sentence: false` + `lm_compose: false`），仓库保持 20/20 绿色；
代码与码表都在位，下一轮只需调这两处策略。

## 3. 可落地改进清单（按性价比排序）

| # | 做什么 | 预期收益 | 成本/风险 | 验证 |
|---|---|---|---|---|
| **R1** | 传统库 `enable_sentence: true` + 共识重排 + **≥5 码门槛** | 五笔短码组句（P1/P2 根治） | 低；需处理垃圾句 | 黄金 20/20 + eval 160 句 |
| **R2** | 「非匹配 Sentence 候选降到匹配者之后」（只降 Sentence 类型） | 消掉拼音垃圾句（P4/§2.3 剩余项） | 低（仍是重排） | 同上 |
| **R3** | 恢复 `wubi_comment`（候选显示五笔码/拼音码） | 混流教学与信任感（P6） | 极低 | console 看 comment |
| **R4** | 提高召回：`max_sentences` 与 poet beam 调参、或候选池先按 LM 剪枝再取 top | P5（66% 正确句进不了候选，是 26% 的主因） | 中；注意耗时（300 句已 6.1s） | eval 召回率（不只是首候选） |
| **R5** | 搜索器准确率（当前整句 26% / 字符 59%） | R1 的收益上限由它决定 | 中；已有 160 句评测集 | eval 160 句 |
| **R6** | 整句词库扩容或改为「短句优先」收录（现 6 万条只覆盖高频句） | 高频场景直接命中 | 低；注意别抢首候选（已验证无副作用） | 黄金 + 抽样 |
| **R7** | 权重**分层内**重标（保持层区间，只调层内次序），而非全局重标 | P8；全局重标已四次失败 | 高；需联合标定 | 黄金 + eval 联合 |
| **R8** | 反查体验：五笔反查拼音、拼音反查五笔一键切换 | P6 延伸 | 低 | 手测 |
| **R9** | **简拼（声母缩写）支持**：`wm`→我们、`jt`→今天（统一表只收了完整音节） | 混流用户高频用法 | 中；需扩码表+防歧义 | 混流用例集 |
| **R10** | **混流分段偏向的修正**：混合库拼音字表 ×0.35 是「简码保护 ↔ 混流组句」的取舍旋钮；试**分层/分场景**取值（而非全局），例如「输入中含非五笔合法码时提高拼音读法权重」 | P2/§2.0 混流误读 | 高；需与黄金用例联合标定 | 黄金 + 混流用例集 |

### 不建议做
- **全局权重重标定**：四次尝试（全词 log / 拼音字表×0.35 / 整链 log / 只重标混合库）**全部破黄金**（§4.17）。
- **把自建候选插进 translator/filter**：引擎会中途提交（§4.15 四路封死）。
- **依赖 `cand.text = ...` 改写**：只对 `SimpleCandidate` 生效，对 Sentence/Phrase 静默无效。

## 4. 关键配置证据（本仓库现状）

```yaml
# egret_wubi_py.schema.yaml
egret_wubi:              # 传统五笔库
  enable_sentence: false         # ← R1 要开（开了五笔短码才能组句，但拼音会有垃圾句）
  enable_completion: true        # ★ 短码补全的关键（kt→吃 ktn）
  initial_quality: 1000          # ★ 恒压混合库（P4 的直接原因）
translator:                      # 混合库（五笔码+拼音音节，script_translator）
  max_sentences: 300             # 召回瓶颈相关
  max_homophones: 7
  max_homographs: 7
  initial_quality: 1             # ← 与 1000 落差 = P4
dynamic_translator:
  lm_compose: false              # 统一搜索器（共识重排）开关
  compose_log_n: 0               # >0 覆盖一元 LM 的 log N（标定用）
# egret.common.yaml (wubi_sentence_speller)
auto_select: true
auto_select_pattern: ^[a-z]+,|^[a-df-zA-DF-Z]\w{3}|^e\w{4}   # 满 4 码顶功上屏（P7，实测非成因）
reverse_lookup: "`[a-z]*'?$"     # 五笔反查拼音（已配）
wubi_comment: 被注释掉            # P6，建议恢复
```
